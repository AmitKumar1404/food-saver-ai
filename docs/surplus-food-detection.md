# Surplus Food Detection

## 1. Module Overview

The Surplus Food Detection module will analyze Inventory and identify food
quantity that may be surplus to normal demand. Its output is a business signal
that later modules can evaluate before creating customer-facing offers.

The first version is intentionally deterministic. It will compare an
Inventory record's `availableQuantity` with a configurable threshold and store
the result as a detection snapshot.

This document defines the initial business and technical design only. No
Surplus Detection Java code, API, database table, AI integration, messaging,
or cache has been implemented yet.

## 2. Business Problem

Restaurants can have available Inventory that is unlikely to be sold through
normal demand. Without an explicit detection step, that quantity may remain
unused even though later FoodSaver workflows could potentially evaluate it for
an offer.

The module should identify **potential surplus** so that the platform can
continue through separate eligibility and safety checks.

The core boundary is:

> Surplus food != unsafe food.

Surplus Detection answers a quantity-oriented business question. It does not
decide whether food is safe, unsafe, spoiled, or eligible for sale. It must not
bypass future deterministic eligibility or food-safety controls.

## 3. Product vs Inventory vs Surplus Detection

The three concepts have separate responsibilities:

- **Product** defines the Restaurant's catalog or menu item, including its
  descriptive and base-pricing information.
- **Inventory** records actual dated quantity and lifecycle state for a
  Product. It is the authoritative source for prepared, available, reserved,
  and sold quantities.
- **Surplus Detection** analyzes an Inventory snapshot and records whether its
  available quantity meets the configured V1 surplus threshold.

Product should not contain current stock, and Inventory should not contain
surplus prediction logic. Keeping Surplus Detection separate allows its rules
to evolve without changing the catalog model or weakening Inventory
invariants.

## 4. V1 Scope

V1 will be:

- Deterministic
- Threshold-based
- Restaurant-ownership-aware
- Based on `Inventory.availableQuantity`
- Configurable rather than numerically hard-coded
- Persisted as a detection record for traceability

V1 will not include:

- AI or LLM decisions
- RAG
- Demand prediction
- Customer-behavior modeling
- Dynamic pricing
- Kafka
- Redis
- Multi-agent workflows
- Food-safety or eligibility decisions
- Automatic Inventory modification
- Automatic Offer creation

Those concerns belong to later, separately reviewed modules.

## 5. Initial Detection Rule

The proposed V1 rule is:

```text
availableQuantity >= configuredThreshold
    -> POTENTIAL_SURPLUS

availableQuantity < configuredThreshold
    -> NOT_SURPLUS
```

Equality is deliberately included: an available quantity exactly equal to the
threshold is `POTENTIAL_SURPLUS`.

The threshold value must not be embedded as a numeric constant in business
logic. The detection service should obtain it from a configuration boundary.

This rule is a simple first implementation, not a demand forecast. It does not
consider historical sales, time of day, weather, events, customer behavior,
expiry, or pricing.

## 6. Proposed Data Model

The proposed table is:

```text
surplus_detections
```

### Fields

#### `id`

- Proposed Java type: `Long`
- Proposed database type: `BIGINT`
- Internal primary key generated by the database
- Never exposed as the public API identifier

#### `public_id`

- Proposed Java type: `UUID`
- Proposed database representation: `CHAR(36)`
- Application-generated external identifier
- Non-null, immutable, and protected by a database unique constraint

#### `inventory_id`

- Proposed Java relationship: required `Inventory`
- Proposed database type: `BIGINT`
- Foreign key to `inventory.id`
- Identifies the Inventory snapshot being evaluated
- Should use lazy loading unless a measured query requires another strategy

#### `detected_quantity`

- Proposed Java type: `BigDecimal`
- Proposed database type: `DECIMAL(12,3)`
- Represents the quantity identified as potentially surplus

For V1:

- `POTENTIAL_SURPLUS`: use the evaluated available quantity as the detected
  quantity.
- `NOT_SURPLUS`: use zero because no quantity was identified as potential
  surplus.

If future audit requirements need the evaluated available quantity even for a
`NOT_SURPLUS` result, introduce a separate explicitly named snapshot field
rather than changing the meaning of `detected_quantity`.

#### `threshold_quantity`

- Proposed Java type: `BigDecimal`
- Proposed database type: `DECIMAL(12,3)`
- Stores the exact threshold used for that detection
- Makes historical results explainable if configuration changes later

#### `status`

- Proposed Java type: `SurplusDetectionStatus`
- Proposed database representation: string with sufficient length
- Stores only `NOT_SURPLUS` or `POTENTIAL_SURPLUS` in V1

#### `detected_at`

- Proposed Java type: `Instant`
- Timestamp when Inventory was evaluated
- Represents the detection event time, not Inventory creation time

#### `created_at`

- Proposed Java type: `Instant`
- System-managed persistence creation timestamp

#### `updated_at`

- Proposed Java type: `Instant`
- System-managed last-update timestamp
- Detection records should normally be treated as historical snapshots rather
  than repeatedly rewritten

### Proposed constraints and indexes

The initial schema should consider:

- Primary key on `id`
- Unique constraint on `public_id`
- Foreign key from `inventory_id` to `inventory.id`
- Index on `(inventory_id, detected_at)` for detection history
- Index on `(status, detected_at)` if operational processing needs recent
  potential-surplus results

The exact index set must be validated against real query patterns before
production. No schema migration is created in this design step.

## 7. Initial Status Model

V1 uses only:

- `NOT_SURPLUS`
- `POTENTIAL_SURPLUS`

`NOT_SURPLUS` means the available quantity was below the threshold used by the
detection.

`POTENTIAL_SURPLUS` means the available quantity was greater than or equal to
that threshold.

Neither status is a food-safety result or final sales-eligibility decision.
Additional statuses must not be added to the V1 implementation merely to model
future workflows.

Possible future lifecycle states may be considered only after eligibility,
Offer, review, and expiration requirements are designed.

## 8. Inventory Relationship and Detection History

The proposed relationship is:

```text
Inventory
    1
    |
    N
SurplusDetection
```

One Inventory record may have multiple detection snapshots over time. Keeping
snapshots can provide:

- An audit trail of repeated evaluations
- The threshold used for each decision
- Visibility into changing available quantity
- Historical inputs for later analytics and demand modeling

Multiple history records are different from accidental duplicate processing.
The module will need an explicit idempotency policy so retries do not create
unintended duplicate snapshots.

V1 should not silently enforce one detection forever per Inventory because
Inventory quantity can change and later re-evaluation may be legitimate.

## 9. Quantity Design

`detectedQuantity` uses `BigDecimal` because Inventory quantities can be
fractional and are stored with decimal precision. `double` and `float` are not
appropriate for authoritative decimal quantity calculations.

The Surplus Detection module reads Inventory quantity; it does not rewrite or
rebalance it.

The Inventory invariant remains:

```text
preparedQuantity =
    availableQuantity + reservedQuantity + soldQuantity
```

Surplus Detection must not:

- Subtract detected quantity from available quantity
- Reserve quantity
- Mark quantity as sold
- Change prepared quantity
- Infer a food-safety state

Future reservation or Offer workflows must use controlled Inventory business
operations that preserve the invariant.

## 10. Configurable Threshold

A configurable threshold is required because a suitable surplus signal can
vary between businesses and Products. A hard-coded number would mix deployment
configuration with business logic and require code changes for operational
tuning.

The first implementation should retrieve a platform-level threshold from an
external configuration source through a clear configuration boundary. The
actual property name, defaulting policy, and failure behavior must be decided
when implementation begins.

Potential future configuration precedence could include:

1. Platform default
2. Restaurant override
3. Product or Product-category override

That hierarchy is not implemented yet. Future design must define validation,
units, precedence, auditability, and behavior when configuration is missing or
invalid.

The threshold used for each evaluation should be copied into
`threshold_quantity` so a historical result remains explainable after
configuration changes.

## 11. Service Architecture

Responsibilities should remain separate:

```text
InventoryService
        ↓
SurplusDetectionService
```

`InventoryService` owns Inventory creation and future controlled quantity
operations.

`SurplusDetectionService` should:

1. Resolve the Restaurant and ownership context.
2. Load the requested Inventory through an ownership-aware lookup.
3. Obtain the configured threshold.
4. Read the Inventory available quantity.
5. Apply the deterministic rule.
6. Build and save a detection snapshot.
7. Return a response DTO.

Surplus logic should not be added directly to `InventoryService` because:

- Inventory quantity management and surplus analysis have different reasons
  to change.
- Detection rules will evolve independently.
- Separate transaction and authorization policies may be required.
- Testing becomes clearer when quantity accounting and analysis are isolated.
- Future AI assistance must not gain direct access to Inventory mutation.

The implementation should avoid circular service dependencies. A dedicated
read boundary or ownership-aware repository query may be preferable if one
service calling another would blur responsibilities.

## 12. Future API Concept

A future endpoint could be:

```text
POST /api/v1/restaurants/{restaurantPublicId}/inventory/{inventoryPublicId}/surplus-detection
```

### Conceptual request

The initial request may require no business fields because the Inventory
identifier comes from the path and the threshold comes from configuration.
If idempotency is required, its key should use a standard request-header or
explicit contract designed for that purpose.

Clients must not supply:

- Detected status
- Detected quantity
- Threshold quantity
- Internal Inventory ID
- Audit timestamps

### Conceptual response

A future response could include:

- Detection public ID
- Inventory public ID
- Detected quantity
- Threshold quantity used
- Status
- Detection timestamp
- Creation and update timestamps

### Conceptual HTTP behavior

Potential response semantics to design during implementation include:

- `201 Created` for a newly persisted detection snapshot
- `404 Not Found` for a missing Restaurant or ownership-scoped Inventory
- `409 Conflict` for a duplicate idempotent request when applicable
- `500 Internal Server Error` only through safe centralized handling for
  unexpected failures

No endpoint or DTO is implemented by this document.

## 13. Future Processing Flow

The intended module sequence is:

```text
Inventory
    ↓
Surplus Detection
    ↓
Potential Surplus
    ↓
Eligibility / Safety Rules
    ↓
Offer
    ↓
Customer Order
```

Each step has a separate responsibility:

- Inventory is the authoritative quantity state.
- Surplus Detection produces a potential-surplus signal.
- Eligibility and Safety Rules determine whether further action is allowed.
- Offer publishes an approved commercial opportunity.
- Customer Order drives reservation and sale workflows.

A `POTENTIAL_SURPLUS` result must never skip the eligibility/safety layer and
create an Offer directly.

## 14. Food-Safety Boundary

The module must enforce these architectural statements:

- Surplus Detection does not mean food is safe.
- Surplus Detection does not mean food is unsafe.
- Quantity and demand signals are not safety evidence by themselves.
- Food eligibility and safety belong to a dedicated deterministic rules layer.
- AI cannot override hard food-safety or eligibility controls.
- Human or qualified oversight must remain available where required.
- RAG content cannot be treated as unrestricted authority for bypassing
  deterministic controls.

RAG may later retrieve approved information to support explanations or
workflows, but retrieved text must be validated, scoped, versioned, and
subordinate to authoritative rules.

## 15. Concurrency and Consistency

Future implementation must address the possibility that Inventory changes
while detection is running.

### Stale Inventory state

The service could read available quantity, calculate a result, and save it
after another transaction changes Inventory. The saved detection would then
describe an earlier state.

A production design should decide whether a detection is:

- An intentional point-in-time snapshot, or
- Required to represent the latest committed Inventory state

If it is a snapshot, the evaluated quantity, threshold, and timestamp must make
that explicit.

### Optimistic locking

Inventory already has `@Version`. Merely reading the version does not
automatically fail when another transaction updates Inventory unless the
workflow performs an appropriate version check or lock. Implementation should
define whether to:

- Re-read before saving
- Use optimistic locking intentionally
- Store the evaluated Inventory version in the detection snapshot
- Retry when safe
- Return a conflict when the state changed

These choices are deferred.

### Transaction boundaries

Inventory lookup, ownership validation, threshold resolution, deterministic
calculation, and persistence of the detection should form a clear service-layer
transaction. The transaction must not directly mutate Inventory.

### Duplicate requests and idempotency

Repeated client retries can create multiple snapshots with the same inputs.
Future design should distinguish:

- A legitimate later re-evaluation
- A retry of the same request

Possible approaches include idempotency keys, a request identifier, or a
carefully defined time/version-based uniqueness rule. No idempotency mechanism
is implemented yet.

## 16. Future AI Integration

Future AI may assist with:

- Demand forecasting
- Surplus probability estimation
- Preparation recommendations
- Pricing recommendations
- Customer recommendations
- Workflow prioritization and orchestration

AI output must remain advisory. AI must not:

- Directly modify Inventory
- Break quantity invariants
- Mark food safe or unsafe without authoritative rules
- Bypass eligibility checks
- Create unrestricted Offers
- Execute tools without scoped permissions, validation, and auditability

Deterministic V1 behavior provides a stable baseline against which future model
quality can be evaluated.

## 17. Future Kafka Integration

Possible future events include:

- `FoodInventoryUpdated`
- `FoodSurplusDetected`
- `OfferCreated`

Events should be published only after the authoritative database transaction
commits. A transactional outbox pattern may be considered to avoid divergence
between database state and event publication.

Event schemas should be versioned and contain public identifiers rather than
leaking internal database IDs. Kafka is not part of V1.

## 18. Future Redis Integration

Potential future Redis uses include:

- Caching calculated demand or surplus read models
- Short-lived workflow state
- Rate limiting
- Idempotency records

Redis must not become the source of truth for Inventory quantity or detection
history. Cache invalidation, key ownership scope, TTLs, failure behavior, and
consistency with MySQL must be explicitly designed.

Redis is not part of V1.

## 19. Testing Strategy

### Deterministic rule tests

- Available quantity below threshold → `NOT_SURPLUS`
- Available quantity equal to threshold → `POTENTIAL_SURPLUS`
- Available quantity above threshold → `POTENTIAL_SURPLUS`
- `POTENTIAL_SURPLUS` records the evaluated available quantity
- `NOT_SURPLUS` records zero detected quantity
- Threshold used by the decision is persisted

### Ownership and resource tests

- Missing Inventory is rejected
- Missing Restaurant is rejected
- Inventory owned by another Restaurant is not accessible

### Persistence and duplicate tests

- Detection snapshot is persisted with public ID and timestamps
- Multiple legitimate snapshots can be retained for history
- Retried duplicate requests follow the future idempotency contract

### Concurrency tests

- Inventory changes during detection
- Stale Inventory version behavior
- Concurrent duplicate detection requests
- Retry or conflict behavior when the evaluated state changes

### Safety-boundary tests

- Detection never changes Inventory quantities
- Detection never assigns a food-safety state
- A potential-surplus result cannot bypass future eligibility rules

## 20. V1 Limitations

Threshold-based detection:

- Does not predict future demand
- Does not understand customer behavior
- Does not understand events, weather, or seasonality
- Does not determine food safety
- Does not determine final sales eligibility
- Does not dynamically optimize pricing
- Does not reserve or modify Inventory
- Does not automatically create Offers
- Does not use AI
- Does not use Kafka, Redis, RAG, or agents

The simplicity is intentional. It creates explainable, testable behavior before
introducing probabilistic models or distributed workflows.

## 21. Roadmap

### V1: Deterministic threshold-based detection

- Evaluate available quantity against a configurable threshold
- Persist `NOT_SURPLUS` or `POTENTIAL_SURPLUS`
- Preserve threshold and detection snapshot data
- Maintain strict separation from food-safety decisions

### V2: Historical sales and demand signals

- Add approved historical inputs
- Establish data quality and audit rules
- Retain deterministic fallback behavior

### V3: Demand prediction model

- Estimate future demand and surplus probability
- Measure model quality against the deterministic baseline
- Keep model output advisory and explainable

### V4: Agentic AI workflow

- Coordinate approved tools and module workflows
- Apply scoped permissions and complete audit trails
- Require deterministic validation around all actions
- Preserve human approval where required

### V5: Kafka, Redis, RAG, controlled tool calling, and guardrails

- Publish versioned domain events reliably
- Cache non-authoritative read models and workflow state
- Retrieve approved knowledge through controlled RAG
- Restrict tool access and validate every action
- Add human approval and operational guardrails

At every roadmap stage:

- Deterministic business controls remain authoritative where possible.
- AI assists but does not bypass controls.
- Surplus food is not automatically unsafe.
- Food-safety rules are not invented inside Surplus Detection.
